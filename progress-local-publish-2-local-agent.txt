## Iteration 3 - US-003: Reusable, hardened login detection
- Reworked workers/posting/capture/detect.ts into a three-way detection API:
  new `detectLogin(signal, snapshot, tracker): 'logged_in' | 'not_logged_in'
  | 'blocked'`. SessionSnapshot gains optional `title`; a trimmed,
  case-insensitive full-title match on "Access Denied" (the Akamai denial
  signature) returns 'blocked' BEFORE anything else — it never earns
  sawLoginPage and can never read as logged-in. redirect_off is only honored
  after tracker.sawLoginPage (earned by actually observing the login path);
  cookie AND redirect_off together both required (delegates to the unchanged
  pure isLoggedIn). checkSession() now feeds detectLogin (page.title() added
  to the snapshot) and treats blocked/not_logged_in identically (fail closed
  into the capture timeout).
- 7 new unit tests in detect.test.ts incl. the exact spike flow
  (/login-as-denial → / with denial title → / with normal title) asserting
  blocked/blocked/not_logged_in and that the denial page never sets
  sawLoginPage. All 8 pre-existing isLoggedIn tests untouched and passing.
- Files changed: workers/posting/capture/detect.ts,
  workers/posting/capture/detect.test.ts, specs/local-publish-2-local-agent.md
- Verified: workers/posting typecheck clean; npm test 26/27 (the 1 failure is
  the known parse-ad-output fixture issue from iteration 1 — still not ours).
  Loading compiled detect.js from /tmp pulls in ZERO
  session/stream/server/playwright modules (checked require.cache) — that is
  the "importable without capture server/stream" criterion, proven
  mechanically.
- Learnings for future iterations:
  - IMPORTANT (working-tree landmine): session.ts/stream.ts/server.ts carry

## Iteration 4 - US-004: Auth as part of the transaction (headed login)

- Learnings for future iterations:
  - PLAYWRIGHT KILLS THE PROCESS ON CTRL-C: chromium.launch defaults
    handleSIGINT/handleSIGTERM to true — playwright closes the browser and
    force-exits (130) when a browser is open, BEFORE the agent's graceful
    shutdown (report failed + close) can run; the job strands in
    awaiting_auth, which 409-blocks re-publish. Fix: launch with
    handleSIGINT:false, handleSIGTERM:false anywhere the agent owns
    shutdown. (First suspected tsx signal relay — it wasn't; but the npm
    agent script is now `node --import tsx agent.ts`, in-process, one less
    relay layer. Iteration-2's node tsx/cli.mjs invocation still works.)
  - redirect_off-only signals can NEVER pass the probe (strict US-003:
    sawLoginPage unearned at new_listing_url). agent-auth resolves valid
    sessions via a one-shot seeded-tracker check right after the deliberate
    goto(login_url): non-blocked landing that bounced off the login path =
    already logged in (~3s, no operator). The seed is used once and
    discarded; the operator wait keeps strict semantics. Denial flow can't
    hit it — 'blocked' returns before any tracker state.
  - A stranded awaiting_auth/posting posting can be reset via
    POST /api/publish-jobs/report {status:'failed'} with the agent token —
    the recovery path for any crashed-agent test.
  - `cd X && (loop) & PID=$!` backgrounds the cd too — the main shell never
    changes dir and the next command runs from the wrong cwd. cd on its own
    line before backgrounding.
  - Unexplained one-off: during e2e run 1 the status recorder saw
    awaiting_auth revert to posting for ~4s then back, with only 1 claim +
    1 report in the dev-server log (writes are atomic renames). Never
    reproduced across 3 later runs with md5 watching. If seen again,
    suspect next-dev read anomaly / multi-worker fs weirdness — not agent
    behavior.
  - US-005: authenticate() returns {browser, context, page, usedHeadedLogin}
    — post in that context, then browser.close() in finally (agent.ts
    already does the close + the posting flip). verify-agent-auth.ts's mock
    marketplace + Xvfb :98 harness is the template for driving the posting
    flow without real sites; extend it with a mock listing form.
  - US-006 AC-1 (log cookie names on every successful capture) is already
    satisfied by finishLogin's names-only log line.

  `PostContext` in post-common.ts ({page, outputDir, platform?}) — the caller
