# Progress — ad-photos feature (specs/ad-photos.md)

## Iteration 1 - US-001: Photo upload API endpoint
- Implemented `POST /api/tasks/[id]/photos`: multipart upload of one photo into
  `workers/workspace/outputs/<taskId>/photos/`, with 404 for unknown tasks and
  400 for bad filename pattern, traversal, disallowed extension, and >15 MB.
- Files changed:
  - dashboard/app/api/tasks/[id]/photos/route.ts (new)
  - specs/ad-photos.md (checked off US-001)
- Verified with curl against `npx next dev -p 3001` (temp task created and
  DELETEd afterwards): valid upload → 200 + file on disk; bad ext / oversize /
  traversal / bad pattern → 400; unknown task → 404. `npx tsc --noEmit` clean.
- Learnings for future iterations:
  - Path resolution pattern for reaching workers/ from dashboard route
    handlers: `path.resolve(process.cwd(), '..')` (same as files/[...path] and
    posting-auth routes). config/paths.json is NOT read by the dashboard.
  - Filename policy chosen: REJECT (400) anything containing `/`, `\`, or `..`
    rather than silently basename-sanitizing — the spec's curl checklist
    expects an error status for traversal filenames. Note `00_..jpg` also gets
    rejected (contains `..`) even though it matches the regex.
  - App Router route handlers have no body-size limit config; `request.formData()`
    handled the 15 MB+ test file fine — no route config needed.
  - Dev-server workflow: start `npx next dev -p 3001` in background with pid
    file, poll `/api/tasks` until up (~10 s), kill by pid when done. Port 3000
    serves stale production code — never verify against it.
  - The `file` form part arrives as a web `File`; write with
    `Buffer.from(await file.arrayBuffer())`.
  - US-002/003 (PhotoPicker) should generate the `NN_` prefix client-side at
    submit time; the API only validates it.

## Iteration 4 - US-004: Submission uploads photos in order
- Ad Builder submit flow now: POST /api/tasks → sequential POST
  /api/tasks/[id]/photos (primary as 00_<name>, rest 01_/02_… in gallery
  order, original names sanitized to the API's /^[0-9]{2}_[\w.-]+$/ contract)
  → fire run-worker → redirect, with worker/redirect gated on all uploads
  succeeding. "Uploading photo N of M…" progress line; submit stays disabled
  (submitting state spans the upload loop). metadata gains photoCount +
  primaryPhoto at task-create time (no extra PATCH needed).
- Files changed:
  - dashboard/app/ad-builder/page.tsx
  - specs/ad-photos.md (checked off US-004)
- Verified: `npx tsc --noEmit` clean; headless Playwright run (10 checks) did
  a REAL submit against `npx next dev -p 3001`: starred-2nd-photo became
  00_creek_view.png (space sanitized to _), disk order 00_/01_/02_ correct,
  metadata stamped, progress text + disabled submit observed, redirect OK.
  Test task deleted + outputs dir removed afterwards.
- Learnings for future iterations:
  - REAL submits in verification are dangerous: cron runs run-worker.sh every
    5 min against the SAME tasks.json the 3001 dev server writes. Mitigation
    that worked: page.route-fulfill '**/api/run-worker' with a fake 200 (the
    page fire-and-forgets it), then PATCH the test task to needs_review
    immediately after redirect (worker only claims pending), DELETE at the end.
  - To make the transient upload UI observable, page.route the photos POST
    with `const r = await route.fetch(); await sleep(600); route.fulfill({response: r})`
    — throttles each upload enough to assert progress text + disabled button.
  - sanitizeBasename (page.tsx module level): strip dir components, replace
    [^\w.-] with _, collapse '..' runs to '.' (API rejects any '..'). Reusable
    for US-005 retry (same filenames must be regenerated identically).
  - photoCount/primaryPhoto ride the initial POST metadata (metadata is a
    known field — the "unknown fields dropped" rule applies to top-level Task
    keys like postings, not metadata contents).
  - US-005 note: upload loop currently throws on first failure (remaining
    queued photos do NOT continue) and a failed run leaves the created task
    behind with partial photos — exactly the gap US-005 is scoped to fix
    (per-file error state, retry-only-failed, proceed-if-≥1-succeeded).

## Iteration 5 - US-005: Upload failure handling in the form
- Reworked the Ad Builder submit flow around a frozen "upload plan"
  (UploadEntry[]: photoId + file + filename + queued/uploaded/failed +
  error). Uploads continue past failures; worker fire + redirect happen only
  when every entry is uploaded and >=1 landed. Failure panel replaces the
  submit button: "N of M photos failed to upload" + "Retry failed uploads"
  (re-sends only failed entries against the SAME taskId — no duplicate task).
  Removing a failed photo from the picker drops it from the retry set and the
  panel flips to a "Continue" button (guarded on >=1 uploaded); on continue,
  metadata.photoCount/primaryPhoto are PATCHed if they went stale. Task-create
  failure shows an inline error and attempts zero uploads. PhotoPicker gained
  an optional uploadErrors prop (photoId -> message): red border + message on
  the failed tile (error border trumps primary teal, drag style trumps both).
- Files changed:
  - dashboard/app/ad-builder/page.tsx
  - dashboard/components/PhotoPicker.tsx
  - specs/ad-photos.md (checked off US-005)
- Verified: `npx tsc --noEmit` clean; headless Playwright run (20 checks,
  all pass) against `npx next dev -p 3001`: task-create 500 -> inline error +
  0 uploads; route.abort('failed') on upload #2 -> red tile w/ "Network
  error", summary text, no worker call, no redirect, photo #3 still
  attempted; retry re-sent exactly 1 request and finished (disk 00_/01_/02_,
  metadata intact); remove-failed -> Continue path left 00_+02_ on disk and
  PATCHed metadata to photoCount=2. Failure-state screenshot inspected.
- Learnings for future iterations:
  - Freezing filenames in the plan at first submit is what makes retry safe:
    already-uploaded NN_ names must never be recomputed after a removal, or
    disk order reshuffles. Gaps in the NN_ sequence (e.g. 00_, 02_) are fine —
    listPhotos() only sorts.
  - taskId in state is the retry anchor: resubmit/retry with taskId set skips
    POST /api/tasks entirely, so flaky uploads can't create duplicate tasks.
  - route.abort('failed') in Playwright makes fetch throw — exercises the
    catch branch ("Network error"), distinct from !res.ok API errors.
  - Bracketed Tailwind classes can't be targeted with normal CSS selectors in
    tests; `div[draggable="true"][class*="FF4D4D"]` works for "tile in error
    state".
  - getByPlaceholder('40') collides with the comps textarea placeholder — use
    { exact: true }.
  - US-007/008 (posting failure UX) are dashboard-only; US-006 is the next
    story and lives in workers/posting (preflight photo check before browser
    launch).

## Iteration 6 - US-006: Poster fails fast when photos are missing
- Added requirePhotos(outputDir, taskId) to workers/posting/post-common.ts
  (throws "No photos found in outputs/<taskId>/photos — upload photos and
  Retry" when listPhotos() is empty; returns the list otherwise) and call it
  in post.ts right after computing outputDir — BEFORE parseAdOutput and any
  browser launch, so a photo-less task fails in ~2s with only that message on
  stderr. Platform scripts untouched; with photos present the check is a pure
  pass-through, so posting behavior is unchanged.
- run-poster.sh: ERR_MSG capture now trims trailing whitespace (tr '\n' ' '
  left a trailing space), so a one-line error lands in lastError byte-for-byte.
- Files changed:
  - workers/posting/post-common.ts (requirePhotos)
  - workers/posting/post.ts (preflight call)
  - workers/posting/post-common.test.ts (new test; 12/12 pass)
  - workers/run-poster.sh (ERR_MSG trim)
  - specs/ad-photos.md (checked off US-006)
- Verified: `npm run typecheck` + `npm test` clean in workers/posting; then
  end-to-end — created a temp task with a queued landmodo posting and no
  photos, ran the real `bash workers/run-poster.sh` with
  DASHBOARD_URL=http://localhost:3001, confirmed postings[0] became
  {status: failed, attempts: 1} with lastError exactly equal to the expected
  message (string-compared), task DELETEd after.
- Learnings for future iterations:
  - A dev server on 3001 may already be running from another session
    (EADDRINUSE) — check `ss -tlnp | grep 3001` + /proc/<pid>/cwd; if it's
    `next dev` in this repo it serves current source and can be reused (don't
    kill a server you didn't start).
  - The poster cron (*/5, # COMMAND-CENTER-POSTER) targets port 3000 against
    the SAME tasks.json — a test task with a queued posting is visible to it.
    Mitigations: run run-poster.sh with the DEFAULT lockfile (mutually
    excludes the cron run), keep the window short, DELETE the task right away.
    With the preflight in the working tree a stray pickup is browser-less.
  - Put preflights in post.ts BEFORE parseAdOutput: a hand-made test task has
    no ad output files either, so a later check would be masked by the
    "cannot read <platform>.md" error.
  - run-poster.sh error plumbing is `tail -n 3 stderr | tr '\n' ' ' | head -c
    500` — multi-line errors get joined; keep operator-facing errors to one
    line if they must survive verbatim.
  - US-007 (failure popover) can rely on lastError now being exact and on
    screenshotPath being absent for preflight failures (no browser = no
    screenshot).

## Iteration 8 - US-008: Permanently-failed postings banner on the tasks page
- New dashboard/components/PostingFailureBanner.tsx, mounted in
  app/tasks/page.tsx between the header and the filter tabs, fed the same
  `tasks` state the 30s poll refreshes. Shows an amber (#D4A04D tinted
  border/bg) banner when any posting is failed with attempts >= 3:
  "N posting(s) need attention" (singular/plural handled) + one underlined
  task-title link per affected task (/tasks?focus=<id>). Dismiss (×) stores
  every currently-failed `taskId:platform` key in sessionStorage
  ('dismissed-posting-failures'); the banner renders only when some failed
  key is NOT in that set, so a NEW permanent failure reappears it while
  already-dismissed ones stay quiet. Resolved failures drop their keys from
  the computed set, so the banner disappears on the normal refresh cycle.
- Files changed:
  - dashboard/components/PostingFailureBanner.tsx (new)
  - dashboard/app/tasks/page.tsx
  - specs/ad-photos.md (checked off US-008)
- Verified: `npx tsc --noEmit` clean; headless Playwright run (15 checks,
  all pass) against the already-running `next dev -p 3001`, with
  page.route('**/api/tasks') fulfilling fake task fixtures so NO real
  tasks.json data was touched: no banner for failed/1+posted; banner
  appeared via a real 30s interval tick (no reload) with correct singular
  text + focus link; plural count across 2 tasks; dismiss -> hidden + 3
  keys in sessionStorage; dismissal survived reload; new failure (task-c)
  reappeared banner with updated count; all-resolved -> no banner.
  Screenshot inspected — matches dark-minimalism rules.
- Learnings for future iterations:
  - `?focus=<id>` is NOT actually consumed anywhere in the dashboard (no
    useSearchParams in app/ or components/) — readme.md claims deep-link
    support but it's aspirational; links with that href are still the right
    contract.
  - Fully faking GET /api/tasks with page.route is the cleanest verification
    isolation yet: zero shared-state risk from cron/worker/poster, and you
    can flip the response object between phases to drive the UI. Route
    handlers persist across page.reload().
  - sessionStorage must be read in useEffect (not a useState initializer) in
    client components — they still SSR-render once and sessionStorage is
    undefined server-side; a `loaded` flag avoids a flash-then-hide.
  - Dismissal semantics that satisfy "reappears on NEW failure": store the
    set of dismissed posting keys, show when any current key is missing from
    it — no timestamps or counters needed.
  - This was the last story: next iteration is the Ship step (feature-log
    summary in specs/specs.md, readme.md fixes, Status -> Implemented).
