# Agent Notes

Reusable patterns for working in this repo.

- **Config files can't be imported by dashboard code.** The Next.js app lives in `dashboard/` and uses Turbopack, which refuses to bundle imports from outside that directory — `import x from '../../config/foo.json'` is a build error even though `tsc` accepts it. Server API routes read `config/` via `fs` from `path.resolve(process.cwd(), '..')`; client components fetch those routes (e.g. `GET /api/posting-platforms`).
- **Typecheck:** `cd dashboard && npx tsc --noEmit` (no npm script). Posting scripts: `cd workers/posting && npm run typecheck && npm test`.
- **Port 3000 is production** (`npm start` via @reboot cron, serves stale compiled code). Never test against it or restart it. Verify with a temp `npx next dev -p 3001` — start it with `DASHBOARD_URL=http://localhost:3001` so spawned worker/poster scripts call back to the dev server, then kill it and clean up temp tasks/logs.
- **All task writes go through the API** (`/api/tasks`), never direct edits to `dashboard/data/tasks.json`, to preserve the write mutex. `POST /api/tasks` drops unknown fields (e.g. `postings`) — attach those via PATCH after create.
- **Browser verification:** Playwright is installed under `workers/posting/node_modules` with headless chromium — `require('<root>/workers/posting/node_modules/playwright')` from any Node script. Against `next dev`, first hit of a route compiles for ~10s; poll the API for expected state rather than waiting on DOM changes. Always browse to `http://localhost:<port>`, not `127.0.0.1` — Next dev treats other hosts as cross-origin and blocks its own script chunks, so pages render server HTML but never hydrate (client components stay in their initial state with no error).
- **Secrets:** `workers/posting/auth/*.json` are marketplace sessions (gitignored) — never expose via the files API or logs.
- **`workers/posting` tests assert against live workspace deliverables.** `parse-ad-output.test.ts` parses real files under `workers/workspace/outputs/task-…/`, so editing those ad outputs (e.g. a DREAMS revision appending the `(Property: …)` nickname tag) breaks `npm test` with no code change. If that suite fails, diff the sample task's outputs before suspecting your change.
- **Shared env vars live in the project-root `.env.local`** (Dialpad keys, `AGENT_TOKEN`). Nothing auto-loads it — Next.js only loads `dashboard/.env.local` — so code that needs a root var reads `process.env` first and falls back to parsing the root file (see `readProjectEnvVar` in `dashboard/lib/agent-auth.ts` and in `workers/posting/agent.ts`). When testing with `next dev`, pass vars on the command line instead.
- **Investment Dominator writes are production.** `workers/patlive-intake/` and the `glenn-rink-api-load` output talk to the live CRM; there is no property delete endpoint. Experiment only on the labeled `[API TEST]` property 5693, and never post to a real record without a read-back diff. Tests: `python3 -m unittest discover -s workers/patlive-intake`. There are two APIs: the legacy `/my/api/*.php` (API key) and the 2.0 REST API at `api.investmentdominator.com/v1` (CRM login JWT), which is the only route to Record Notes and Files and the only thing the 2.0 UI reads. Endpoint notes for both: `~/claude/followupdominator/api_reference_investment_dominator.md`.
- **Landmodo poster is mapped to the live site, not guessed.** Landmodo is a Brilliant Directories site: create at `/account/properties/newgroup`, photos at `/account/properties/addphotos/<hash>` (10 per property, 10 MB per batch), listing URL from the My Properties row. The list is a server-side DataTable (wait for rows, not the page), the upload dialog is SweetAlert2 v6 (`.swal2-modal`), and a logged-in member stays parked on `/login`, so `login_success.logged_in_selector` (the create form) is the session signal. APN is required: `metadata.apn` or an "APN …" mention in task notes. To re-map after a redesign, run `npx tsx recon-form.ts <platform> <url>` on the machine that holds `auth/landmodo.json` (the operator's laptop, a GitHub clone on `main`) and copy the dumped HTML/PNG back to `.agent-cache/recon/`. The production dashboard on 3000 lacks `/api/resolve-location`, so the agent's "location resolver unavailable" warning is expected.
- **Land.com poster targets the Marketing Hub (`market.land.com`), a React SPA; verified live 2026-10-03 (listing 29013311).** The session signal is the "Add Listing" button (`login_success.logged_in_selector`); the hub re-logs itself from the main land.com cookie, so the popup rarely needs typing. Flow: read the ag-grid (All Listings AND the Draft tab, which All Listings omits), reuse an active match by title or price+acres+state, finish a matching draft, else create via Add Listing in Lat/Long mode from `metadata.latitude/longitude` (the app reverse-geocodes a neighbour's house number into the required "Location Description / Street Address" box; the poster overwrites it with `metadata.location_description`, else "County, ST"). Editor order matters: photos first (an upload reloads the editor and drops unsaved text), then toggles (selected state is the `_selected_` class on the button), then text, then Save, then reload and read the title back, then Publish Changes. Title cap is 75 characters (`config/ad-platforms.json` says so; `metadata.land_com_headline` overrides). Account cap: 5 Active listings, free; drafts and sold do not count. Public URL pattern: `https://www.land.com/property/<acres>-acre(s)-in-<county>-county-<state>/<id>/`. `npm run post -- land_com <task> --dry-run --headed` leaves a saved draft; this app does not work headless.
- **Land Century poster is verified live 2026-10-05 (listing 26439, https://www.landcentury.com/land-for-sale/colorado/100-acres-for-sale-in-fairplay-colorado-26439), mapped from the site's own front-end source.** The account is on the Single Listing plan (one live listing); the Wells NV listing 25178 was unpublished to make room, and the poster turns the site's "Listings limit exceeded" refusal into an error naming the live listings. `landcentury.com` is a Next.js SPA (Ant Design) over `api-prod.landcentury.com`; everything a seller does sits under `/admin` and a logged-out visit bounces to the home page, where the account icon opens the Sign In modal (`#email`, `#password`). The session is `localStorage.apiToken` plus the site's cookies, so `login_success` uses the new `local_storage_key` signal (presence only, never the value) with `form.properties-admin-form` as the DOM marker. The listing form is a five-step wizard (`/admin/listings/form/create`, then `/admin/listings/form/<id>?step=N`): Main Info (listing type, categories multi-select REQUIRED, parcel number, cash price, owner-finance checkbox + price + terms textarea; Next POSTs the create and moves to the new id), Description (a Quill editor, set through the react-quill instance found via the React fiber, typing fallback), Location (latitude/longitude + "Get Location" reverse-geocodes the address; the poster then overwrites state/county, and Street with `metadata.address` or `location_description`), Media (multi-file input, each file uploaded on its own, jpeg/png/webp under 20 MB, first = main image, poster caps at 20), Detailed Info (acres, deed/zoning/road/utilities AutoCompletes, taxes, legal description). **There is no title field**: the site names listings itself ("1.00 Acres for Sale in Fairplay, Colorado"), so the headline goes in as an `<h3>` at the top of the description. Step 4's primary button is "Publish" (sets isPublished); "Save Changes" keeps a Draft, which is what `--dry-run` leaves. Existing listings are read with the session's own token from `/api/v1/users/properties/all` and matched by parcel number, then price + acres. Public URL `https://www.landcentury.com/land-for-sale/<state-name>/<slug>` with `slug` from the property record. Plans: Single Listing $5/mo, Basic $50/mo (30 listings), Pro $100/mo; a non-seller account gets an "Account update required" company form, which the poster reports. Form inputs have no ids or names: every field is found by its Form.Item label (`LANDCENTURY_SELECTORS.item`), so a relabel is a one-line fix. **Never send credentials to `api-prod.landcentury.com`**: every response from it sets an anonymous `landcentury_session` cookie for `.landcentury.com`, which shadows the host-only www login cookie and makes the property write routes answer "Unauthenticated." (the site's own calls pass withCredentials=false); the poster reads with `credentials: 'omit'` and drops any such stray cookies first.
- **ParcelView poster is mapped to the live site (recon dumps 2026-10-04, `.agent-cache/recon/parcelview_com_*`).** WordPress plus the `parcelview3d-saas` plugin, all behind the login (even the REST index). Flow in `post-parcelview.ts`: read `/properties/` cards (match by APN; "n of 50 properties used" is the cap), create at `/new-property/` through the APN search (search type, APN, state code, county, Search Parcels, click `.pv3d-result-item`), fill name/acres/pricing/terrain/features, Save (`#pv3d-panel-save-btn` submits `form#property-form` by ajax and the server redirects to `/edit-property/?id=N`), then on the edit page fill `#pv3d-listing-description` (maxlength 2000), the `listing_status` / `listing_badge` / `listing_kind` selects in the strip above the form, upload photos (15 max, 5 MB each, copyright checkbox first; each file posts by ajax so this only works on the edit page), Save again ("Saved!" in `#pv3d-msg`, then the page reloads), reload and read back. Publish = status `available`; `--dry-run` leaves it `unlisted`. Public URL `https://parcelview.com/listing/<hash>/`, hash from the embed input or the card's Share link, read AFTER the final save: the hash the dry run reports changed when the lot was published (6741… became f5bc…), so a dry-run URL is not the live one. The form says 5 MB per photo but the server drops anything near 1 MB, so the poster re-encodes photos over 900 KB in its own browser and uploads them one at a time. Feature chips are set by property plus a change event, not by click. Verified live 2026-10-04 (property 726). APN is required (`metadata.apn` or an "APN …" mention). Session signal is leaving `/login` when probing `/new-property/`.
- **Landflip poster is verified live 2026-10-13 (listing 426576, https://www.landflip.com/land/426576), mapped from the seller area at `my.landflip.com` and the site's own `/js/app.min.js`.** `www.landflip.com` sits behind Cloudflare and returns 403 to headless browsers and to this server, so the poster never opens the public page (URL built from the id; check it in a normal browser) and all recon runs on the laptop. The seller area is server-rendered jQuery/Foundation: `/listings` grid cards (`#lb<id>`, title, "<acres> Acre : $<price>", Online/Offline + Available/Under Contract/Sold tags), `/listing-add` (one long form, Continue creates and lands on `/listing-photos/<id>`), `/listing-edit/<id>` (same form, Save), `/listing-photos/<id>` (`#file`, one upload per ajax submit then a reload), `/listing-map/<id>` (`#latitude`/`#longitude`, 12 chars, `#show-map`), and the status strip's Turn On (`#visible-btn`, ajax `action=turnon`) as publish. Title is 35 chars from the set `a-zA-Z0-9 - , . + / & $ '` and the site title-cases ALL-CAPS words ("CO" -> "Co", "APN" -> "Apn"), so `config/ad-platforms.json` caps the landflip headline at 35 and the poster reads `metadata.landflip_headline`; city and zip are required (`metadata.city`/`zip`); overrides `landflip_terrain`, `landflip_zoning`, `landflip_access`, `landflip_utilities` (checkbox ids). Entry plan: 1 listing, 10 photos; the "at your listing plan limit" notice shows even at 0 listings and does not block Continue, so the poster trusts the create response instead. A rerun on an Online listing records it and edits nothing.
- **Facebook Marketplace is a post-by-hand platform, on purpose (2026-10-13).** No listing API exists for an individual seller, Meta's terms forbid automated posting, and a browser bot on the operator's own account risks a Marketplace ban, so never build a poster for it. `config/posting-platforms.json` marks it `manual: true` (with `manual_steps` and `manual_photo_cap`), `PublishButtons` ignores it, and `dashboard/components/ManualPublishCard.tsx` shows a "Post by hand" card on ad-builder tasks that list the platform: the generated copy with Copy buttons (read from `<workspace>/<key>.md` through the files API), the photos in upload order (primary first, first 10), the create-form link, and a URL box that records the posting through `PATCH /api/tasks/<id>` with the full `postings` array. The ad side is a normal short-form platform in `config/ad-platforms.json` (title 100 best-effort, description 2000; the title must say it is land and where because the listing goes in as an Item for sale, category Other; plain words instead of BLM/HOA/APN). The create form seen 2026-10-12: 10 photos, 1 video, title, price, category, condition, description, location (defaults to the account's home town; set it to the property's town). The generate-ad command lists it with eBay as a mainstream audience.
- **Land-listings.com poster is mapped from the public site and its API docs (2026-10-05), logged-in form not yet seen.** Laravel site: login POST form at `/login` (`#email`, `#password`), account home `/dashboard`, create at `/add-a-listing`, public listing `https://www.land-listings.com/listing/<id>`; `#dashboard-menu` and the POST logout form are the logged-in markers. Fields follow the site's API field contract (title 255, description 50,000 plain text, price, acres, owner_financing, general_location, address/city/state/county/postal_code, mls_number, latitude/longitude, directions, video_url); county must be the site's canonical name, public lookup `GET /api/counties/<ST>`. Publishing needs Premium Standard ($49.95/mo, 20 photos) or Deluxe ($149.95/mo, 100 photos); a Free Account saves Unlisted only with one photo, and the poster refuses a real publish on one. Every field in `post-land_listings.ts` is found by name/id then label text (`LANDLISTINGS_SELECTORS.fields`); the first logged-in recon (`npx tsx recon-form.ts land_listings --login` on the laptop) corrects that block.
- **DREAMS gate scripts call the real `claude` and cost money.** `workers/dreams-gate.sh <output_dir>` spawns one opus judge session per platform (about $1 and a minute for seven). Test the scripts offline with `workers/dreams-gate.test.sh`, which puts a stub `claude` first on PATH; the scripts append `~/.local/bin` to PATH for exactly this reason, so never change that to a prepend. To exercise the worker's reject-and-requeue path, run `workers/run-worker.sh` with `PATH=<stub-dir>:$PATH DASHBOARD_URL=http://localhost:3001 LOCKFILE=/tmp/<name>.lock` against a temp `next dev -p 3001`, then delete the temp task, its output dir, its notes file, the new `workers/logs/worker-*.log` files, and restore `dashboard/data/worker-state.json`. Running the gate on a real task's output dir writes `dreams-scores.json` there; copy the dir to `/tmp` first when you only want to look at scores.

- **Fronts pipeline scripts call the real `claude` and post to the dashboard.** Test offline with `workers/fronts/fronts.test.sh` (stub `claude` and stub `curl` from `workers/fronts/fixtures/`, temp fronts dir, 50 checks). To rehearse the real chain: temp `next dev -p 3001`, then `FRONTS_DRY_RUN=1 DASHBOARD_URL=http://localhost:3001 workers/fronts/run-pipeline.sh <transcript.jsonl> <session_id> <cwd>` (works on a `/tmp/fronts-dry-run-*` copy of `fronts/`; still posts suggestions, so reset `dashboard/data/front-suggestions.json` to `[]` afterwards and delete the copy). Never set `FRONTS_SKIP` to anything but `1` in the worker or DREAMS scripts: it is the guard that stops `claude -p` runs from filing themselves as sessions. The SessionEnd hook is installed with `workers/fronts/install-hook.sh` (edits `~/.claude/settings.json`, idempotent, `--uninstall` reverses). Agents never write `fronts/<slug>/north-star.md`.
- **Calls dashboard (`/calls`) talks to followupdominator on 8100, which is production: never restart 8100 yourself** (restarts are an operator step; write them under Questions). For development run the fake-backed stack: from `~/claude/followupdominator`, `CALLS_API_TOKEN=<throwaway> .venv/bin/python scripts/run_e2e_dev.py 8101 <tmp>/e2e.db <tmp>/id-writes.jsonl` (prints `SESSION=<token>` for `POST /dev/replay`), then `next dev -p 3001` with `DASHBOARD_URL=http://localhost:3001 CALLS_API_URL=http://127.0.0.1:8101 CALLS_API_TOKEN=<same>`. Production needs the same `CALLS_API_TOKEN` value in followupdominator `.credentials/dashboard.env` and the root `.env.local`; send it only as a bearer header (uvicorn logs query strings). One-command check of the whole chain: `workers/calls-e2e/run.sh` (about 55 s, refuses if 3001 or 8101 is busy, cleans up after itself). API contract: followupdominator `docs/api-v1.md`.
