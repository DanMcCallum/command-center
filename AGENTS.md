# Agent Notes

Reusable patterns for working in this repo.

- **Config files can't be imported by dashboard code.** The Next.js app lives in `dashboard/` and uses Turbopack, which refuses to bundle imports from outside that directory — `import x from '../../config/foo.json'` is a build error even though `tsc` accepts it. Server API routes read `config/` via `fs` from `path.resolve(process.cwd(), '..')`; client components fetch those routes (e.g. `GET /api/posting-platforms`).
- **Typecheck:** `cd dashboard && npx tsc --noEmit` (no npm script). Posting scripts: `cd workers/posting && npm run typecheck && npm test`.
- **Port 3000 is production** (`npm start` via @reboot cron, serves stale compiled code). Never test against it or restart it. Verify with a temp `npx next dev -p 3001` — start it with `DASHBOARD_URL=http://localhost:3001` so spawned worker/poster scripts call back to the dev server, then kill it and clean up temp tasks/logs.
- **All task writes go through the API** (`/api/tasks`), never direct edits to `dashboard/data/tasks.json`, to preserve the write mutex. `POST /api/tasks` drops unknown fields (e.g. `postings`) — attach those via PATCH after create.
- **Browser verification:** Playwright is installed under `workers/posting/node_modules` with headless chromium — `require('<root>/workers/posting/node_modules/playwright')` from any Node script. Against `next dev`, first hit of a route compiles for ~10s; poll the API for expected state rather than waiting on DOM changes. Always browse to `http://localhost:<port>`, not `127.0.0.1` — Next dev treats other hosts as cross-origin and blocks its own script chunks, so pages render server HTML but never hydrate (client components stay in their initial state with no error).
- **Poster login window extensions:** `POSTER_EXTENSIONS=proton-pass` (root `.env.local` on the laptop, or the environment for `npm run post --login`) loads Proton Pass into the agent's headed login window. That switches the launch to `chromium.launchPersistentContext` on `.agent-cache/profile/` (extensions load nowhere else); `workers/posting/extensions.ts` resolves an id by copying the newest `Extensions/<id>/<version>` out of the operator's Chrome profiles minus `_metadata` (Chrome refuses unpacked extensions that carry it). The persistent profile keeps its own cookies; `auth/<platform>.json` is still written on every captured login and is seeded into the profile on its first run. Default (unset) behaviour is unchanged. Offline check on this box: `xvfb-run -a npx tsx <script>` with a fake MV3 extension; `npm test` covers the resolver.
- **Secrets:** `workers/posting/auth/*.json` are marketplace sessions (gitignored) — never expose via the files API or logs.
- **`workers/posting` tests assert against live workspace deliverables.** `parse-ad-output.test.ts` parses real files under `workers/workspace/outputs/task-…/`, so editing those ad outputs (e.g. a DREAMS revision appending the `(Property: …)` nickname tag) breaks `npm test` with no code change. If that suite fails, diff the sample task's outputs before suspecting your change.
- **Shared env vars live in the project-root `.env.local`** (Dialpad keys, `AGENT_TOKEN`). Nothing auto-loads it — Next.js only loads `dashboard/.env.local` — so code that needs a root var reads `process.env` first and falls back to parsing the root file (see `readProjectEnvVar` in `dashboard/lib/agent-auth.ts` and in `workers/posting/agent.ts`). When testing with `next dev`, pass vars on the command line instead.
- **Investment Dominator writes are production.** `workers/patlive-intake/` and the `glenn-rink-api-load` output talk to the live CRM; there is no property delete endpoint. Experiment only on the labeled `[API TEST]` property 5693, and never post to a real record without a read-back diff. Tests: `python3 -m unittest discover -s workers/patlive-intake`. There are two APIs: the legacy `/my/api/*.php` (API key) and the 2.0 REST API at `api.investmentdominator.com/v1` (CRM login JWT), which is the only route to Record Notes and Files and the only thing the 2.0 UI reads. Endpoint notes for both: `~/claude/followupdominator/api_reference_investment_dominator.md`.

Public URL `https://www.landcentury.com/land-for-sale/<state-name>/<slug>` with `slug` from the property record. - **BuyWander nightly deal scan runs as `claude -p --chrome` in the operator's own Chrome, not Playwright (built 2026-11-08; the operator wants the marketplace posters migrated to claude-in-chrome the same way).** Cron `# COMMAND-CENTER-BUYWANDER` fires at 23:00 and 00:00 UTC and `workers/buywander/run.sh` exits unless it is 17:00 in America/Denver, so DST needs no crontab edit. The script fetches `GET /api/buywander/seen` (bearer `AGENT_TOKEN`), renders `workers/buywander/prompt.md` into `workers/buywander/runs/<stamp>/`, runs Claude (`BUYWANDER_MODEL`, default sonnet; `BUYWANDER_MAX_ITEMS`, default 40) with only Read, Write and the `mcp__claude-in-chrome__*` tools allowed, then POSTs the output JSON to `POST /api/buywander/runs`, which scores (spread = eBay sold median minus current bid; shipping = a UPS Ground planning estimate in `dashboard/lib/shipping.ts` from the lot's `sizeDescription` ("L: 95.3 cm x W: 57.9 cm x H: 101.6 cm, Weight: 11.567 kg"; greater of actual and L×W×H/139 dimensional weight against an approximate 2026 zone-5 residential rate table, plus additional-handling and large-package surcharges; over 150 lb or 165 in length+girth shows "freight"; lots with only a bin code get `BUYWANDER_DEFAULT_SHIPPING`, $20); max bid = median × (1 − eBay fee) × (1 − target margin) ÷ (1 + pickup cost), shipping deliberately NOT subtracted because heavy lots may sell locally (operator decision 2026-11-08), defaults 13.6%, 40%, 7.25% Utah sales tax, overridable with `BUYWANDER_EBAY_FEE_RATE`, `BUYWANDER_TARGET_MARGIN`, `BUYWANDER_BUYER_COST_RATE`, `BUYWANDER_SHIPPING_MULTIPLIER` in the root `.env.local`; the rule used is stored on each run as `bid_rule`), stores `dashboard/data/buywander-runs.json` and `-seen.json` (gitignored; a lot counts as seen once it is priced with at least one comp or skipped for cause, so over-cap and no-comp lots are retried nightly while live), and emails the finds. BuyWander is a Nuxt SPA over `bwapi.buywander.com`: the grid is `POST /api/site/v1/Auctions/search` with `{pageNumber,pageSize,storeLocationIds:[...],minRetailPrice,sortBy}` (cookie auth, `pageNumber` is ignored in favour of a `searchAfter` cursor, so one page of 200 is used; Salt Lake City id `08dde114-da37-1ddb-6c02-e090d6310000`), retail value is `item.price`, and the public lot URL is `https://buywander.com/auctions?auctionId=<id>` (`/auctions/<id>` 404s). eBay sold comps are read from `https://www.ebay.com/sch/i.html?_nkw=…&LH_Sold=1&LH_Complete=1` cards (`li.s-card`, caption "Sold <date>"), judged by the model for same-product matches; when none match it runs one broader brand-plus-product-type search and tags those comps `match: "loose"` (amber tag on `/deals`, "(loose match)" in the push). Notification is an ntfy push (`dashboard/lib/ntfy.ts`): the route POSTs a summary (title, top five finds by spread, click URL to `/deals`) to `https://ntfy.sh/<BUYWANDER_NTFY_TOPIC>`; the topic in the root `.env.local` is the only secret, so never print it in chat, logs or the UI (`BUYWANDER_NTFY_SERVER` and `BUYWANDER_NTFY_TOKEN` are optional overrides for a self-hosted or access-controlled topic, `DASHBOARD_PUBLIC_URL` for the click link). The push result is stored on the run as `notify` and shown on `/deals`; nothing is pushed for a run with no finds. Email was dropped the same day it was built (the Fastmail token is read-only and the operator prefers a phone push), so runs stored before that carry an `email` field instead. Rehearse with `DASHBOARD_URL=http://localhost:3001 BUYWANDER_MAX_ITEMS=3 workers/buywander/run.sh --now` (about a dollar on sonnet; `--dry-run` skips the POST). The run dir keeps `claude.json`, `claude.log` and `output.json` for the last 14 runs. Never add bidding, watching or cart actions to the prompt.
