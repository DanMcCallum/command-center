## Defect found and fixed

**`import.csv` was written with CRLF line terminators; the sample template uses
LF.** The header therefore differed from `id-import-sample.csv` by one byte per
line (2629 vs 2628 bytes), failing acceptance criterion 1. The README's
verification section had recorded this check as passing.

Fix: rewrote the file replacing `\r\n` with `\n`. Safe because the file had
exactly 36 CR and 36 LF for 36 lines (header + 35 rows), proving no quoted field
contained an embedded newline. Verified after the rewrite that the file is
byte-identical to the original once line endings are normalized. Original kept at
`parts/import.csv.crlf-backup`. README corrected to record both the original
failure and the fix.

## Third rejection, and the actual root cause — 2026-08-03

`or_id` = `6240` was rejected with the same message as the empty value. The
operator then supplied a **real import template**,
`operator-input/seller-submissions/id-import-sample-2.csv` — property 7237,
Glenn's own existing parcel, with `or_id` `6240` in it.

Diffed template vs. our file: 176 columns, identical order, identical names
including the duplicated `tag_ids` column — **except headers 7 and 8**, which an
earlier pass had renamed to `Property State` / `Property County`. That rename is
the bug. It was made in response to ID reporting those two as "unmatched", read
as "ID does not recognise our column names" when it actually meant "no column
supplied these required fields". So the rename broke two working columns, and the
importer surfaced the failure against `or_id` downstream.

Two lessons worth keeping: an importer's field-name error may be naming *its*
schema, not yours; and three rounds were spent theorising about `or_id` because
nobody had the import template — the export was being used as a stand-in for it
from the very first acceptance criterion.

`or_id` 6240 independently cleared before rebuilding, in case it was also wrong:

- Tallied `owner_id` across all 8,175 readable property rows — 6,957 distinct
  owners, sharing routine: 347 own 2 properties, largest owns **101**. So 35 rows
  on one owner id is an ordinary shape, not a constraint violation.
- Combined with the earlier walk pinning 6240 to property 7237 at Glenn's
  assessor-derived mailing address, and now the operator's own sample row naming
  him on 6240, the value is confirmed from three directions.

Rebuild applied to `import.csv` (rejected file kept at
`parts/import.csv.rejected-orid6240`): headers restored to `p_state` / `p_county`;
`p_county` values `PINAL COUNTY` → `Pinal` per the template's convention;
`u_id` = `1`, `p_property_type` = `LAND`, `m_recipient` = `Glenn Rink` from the
template row; `p_id` empty for new records; `or_id` `6240` unchanged. Asserted
header byte-identical to the template, 36 lines × 176 columns. Split files
regenerated from the same build.

**Tags finding, held back deliberately.** The template has a `tags` column

The earlier conclusion — tags are id-only, no listing endpoint, therefore
UI-only — was right about `tag_ids` and wrong about the ceiling. Left empty on

## Fourth rejection — the header revert was wrong — 2026-08-03

Rebuilding to the template's `p_state` / `p_county` produced: *"missing the
following header(s)! Property County, Property State"*. So the **wizard requires
the display names**, and the earlier pass's rename was correct after all. My
previous entry above called that rename the root cause; it was not. Corrected.

What the two conflicting facts actually mean: `id-import-sample-2.csv` is a valid
file *layout* (176 columns, order, duplicate `tag_ids`) but its raw column names
for state and county are not what the wizard's header matcher accepts. `p_city`
matches fine under its raw name — only those two are special, most likely because
ID holds more than one state/county field and cannot disambiguate.

Rebuilt per the operator's instruction: headers `Property State` / `Property
County` restored, and the values for state, county and city taken **verbatim from
the old file**, matched row-by-row on APN rather than row order (`PINAL COUNTY`
again, not `Pinal`). Kept from the template pass: `u_id` `1`,
`p_property_type` `LAND`, `m_recipient` `Glenn Rink`, `or_id` `6240`.

That leaves attempt 3's exact configuration plus those three columns. If `or_id`
fails again, those three are eliminated and the untested fix — **leave `or_id`
unmapped in the wizard's manual header-match step** — is the next lever. The
error screen offers that mapping UI, so it can be tried without another file.

Rejected files kept: `parts/import.csv.with-orid` (attempt 2, `or_id` empty),
`parts/import.csv.rejected-orid6240` (attempt 3), and
`parts/import.csv.rejected-tmpl-headers` (attempt 4).

Standing lesson from four rounds: every diagnosis here has been a guess about a
closed-source wizard's validator, and two of them were confidently wrong in
opposite directions. The only reliable signal is what the wizard says on upload —
so change one variable per attempt and keep the rejected file each time.
